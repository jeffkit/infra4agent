# 提 issue 须知（issue-keeper 管线协作约定）

> 适用范围：任何向 `jeffkit/*` 子仓提报 issue 的 agent（人工或自动）。
> 背景：issue-keeper 守护进程会**读取 issue 正文**做依赖排序与派发决策——正文格式不达标会导致排序错误、卡单或重复动工。
> 创建：2026-10-04（okguitar 场景 gap 批次实践沉淀）。

## 一、必填头部（keeper 解析依赖所必需）

每单正文**第一段**必须是 blockquote 头部：

```
> 优先级 **P1** · 依赖：无
```

带硬依赖时：

```
> 优先级 **P1** · 依赖：depends-on: #117（未终态时 keeper 自动 hold）
```

- **优先级**：`P0` / `P1` / `P2`，语义约定：
  - **P0** = 安全漏洞 / 数据丢失或泄露 / 进程级或全租户故障 / 管线不可用；
  - **P1** = 功能正确性、可靠性、可观测性缺口（有明确场景影响）；
  - **P2** = 体验、治理、文档与一致性。
- **硬依赖必须用字面量 `depends-on: #N`**（同仓编号，可多条，逗号或多个 depends-on 均可）。
  keeper 派发时解析：依赖项未到终态（`processed`）则本轮 hold、每轮重查；依赖 run 以失败收尾也视为 settled（不级联阻塞）。
  **不要**用「依赖 #N」「见 #N」等自然语言表达硬依赖——keeper 不识别，会失去排序保障。
- 正文中对**同仓批内其他未处理单**的 `#N` 引用会自动产生**软排序边**（被引用者先跑）。无关引用会干扰排序，引用需谨慎。

## 二、正文结构（可核对、可验收）

```
基线 HEAD = <git -C <repo> rev-parse --short origin/main>
## Summary   — 证据清单：逐条 path:line + 关键代码摘录（必须亲读过的行）
## 影响      — 具体到场景：谁在什么情况下会踩、代价是什么
## 建议      — 修复方向 + 验收条件（可执行、可断言）
## 边界      — （可选）不做什么、与相邻单的关系
```

- 「缺失」类断言（如 grep 零命中）必须给出反证命令或可复现步骤。
- 每单只装**一个可独立修复的 gap**；大改造拆单链（tracking 单 + 子单，子单头部写 `depends-on` 链）。
- 提报前先 `gh issue list -R <repo> --state all` 查重（含 closed——已否/已修的方案不要重提）。

## 三、定位与账号

- **进哪个仓**：按 gap 所属代码仓提报；跨仓同根问题**拆开提**，正文互相引用（不合并成单）。
- **提报账号**：`okguitar`（历史约定）。注意 web-bridge 为私有仓，okguitar 已是协作者（push）。
- **标题**：`type(scope): 一句话`，type ∈ `fix` / `feat` / `security` / `perf` / `refactor` / `chore` / `test`，正文中文。

## 四、验收约定（谁提谁被验收）

- 修复落地后由提报方（或验收值守）做**代码级验收**：读修复 commit 的**完整 diff**，逐条对照 issue 正文的证据点核对实现——**不得仅凭 journal、门禁声明或 commit message 下结论**；能便宜复跑的定向测试优先实跑，跑不动时必须在回评里写明本次验证方式与局限。
- **可观测性相关单**：凡"运行时可见性"条目，除代码 diff 核对外还须在 **Langfuse** 中确认对应记录存在（recursive #124 是接入目标）方可通过。
- 通过 → 回评「✅ 验收通过」+ 逐点证据并关闭；不通过 → 回评具体缺口并保持开启。

## 五、禁止事项

- 禁止无证据的推测写进 Summary（存疑项放"未证实"附注单列）。
- 禁止把多个不相关 gap 塞进同一单。
- 禁止修改既有关闭单的结论性内容（补充信息用新评论）。
- 禁止擅动正文里的 `depends-on`（会改变 keeper 排期；需要调整时通知值守）。
